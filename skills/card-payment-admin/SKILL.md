# 카드 결제 관리자 화면 (대사·정산) 개발 가이드

자영업자/상점 관리자가 모바일 앱에서 **카드 거래, 일별 매출, 불일치(대사) 내역, 정산**을 확인하는 화면을 만들기 위한 설계 규칙.
기준 PG는 토스페이먼츠이며, 다른 PG도 "거래 조회 / 정산 조회 API" 구조가 같으면 그대로 적용한다.

## 0. 핵심 전제 (먼저 확인)

1. **대사 화면은 PG가 주지 않는다.** PG는 자기 거래·정산 데이터만 준다. 우리 주문/결제 데이터와 비교하는 기능은 우리 시스템이 만든다.
2. **앱은 PG API를 직접 호출하지 않는다.** 시크릿 키는 서버에만 둔다. 앱 → 우리 백엔드 → PG 구조 고정.
3. **대사는 배치로, 화면은 결과 조회만.** 앱 화면에서 실시간으로 PG API를 호출해 비교하지 않는다(조회 최대 60초, 429 위험).
4. 금액은 정수(원 단위)로 다룬다. float 금지.

## 1. 전체 아키텍처

```
[PG 토스페이먼츠]
   ▲  GET /v1/transactions (거래)
   │  GET /v1/settlements  (정산)
   │  Webhook (상태 변경)
[우리 백엔드]
   ├─ 결제 승인/취소 시 payment, payment_tx 저장 (실시간)
   ├─ 일 배치: PG 거래 수집 → pg_transaction 저장 → 대사 → recon_result
   ├─ 일 배치: PG 정산 수집 → pg_settlement 저장
   └─ 관리자 API (조회/엑셀 생성)
[모바일 앱 관리자 화면]
   └─ 관리자 API 결과만 표시
```

상세 API 스펙: `references/toss-api.md`
대사 로직/테이블: `references/reconciliation.md`

## 2. 화면 구성 (필수 5개)

| # | 화면 | 목적 | 주요 데이터 |
|---|------|------|-------------|
| 1 | 홈(요약) | 오늘/어제 매출과 이상 여부를 한눈에 | 승인액, 취소액, 순매출, 불일치 건수, 다음 정산 지급 예정액 |
| 2 | 일별 매출 | 날짜별 우리 금액 vs PG 금액 비교 | 일자, 우리 순매출, PG 순매출, 차액, 대사 상태 |
| 3 | 거래 목록 | 개별 승인/취소 건 조회 | 일시, 주문번호, 금액, 카드사, 마스킹 카드번호, 할부, 상태, 대사 상태 |
| 4 | 불일치 내역 | 맞지 않는 건 확인·처리 | 불일치 유형, 우리 금액, PG 금액, 차액, 처리 상태, 메모 |
| 5 | 정산 내역 | 언제 얼마 들어오는지 | 매출일, 지급일, 결제액, 수수료, 지급액 |

+ 각 목록 화면에 **엑셀 다운로드** 버튼.

### 화면별 규칙

**홈(요약)**
- 불일치 건수가 1건 이상이면 상단에 경고 배너 → 탭하면 불일치 내역으로 이동.
- 마지막 대사 배치 실행 시각을 표시한다("어제 03:10 기준"). 실시간 아님을 명확히.

**일별 매출**
- 기본 기간: 최근 7일. 기간 필터(오늘/7일/30일/직접 선택, 최대 92일 권장).
- 차액 ≠ 0인 날짜는 강조 색상 + 탭 시 해당 일자의 불일치 내역으로 이동.
- 우리 금액 / PG 금액 / 차액 3개를 반드시 같이 보여준다. 하나만 보여주면 대사 화면이 아님.

**거래 목록**
- 필터: 기간, 거래 유형(승인/취소/부분취소), 대사 상태(일치/불일치/PG누락/우리누락), 카드사.
- 검색: 주문번호(orderId), 승인번호.
- 정렬: 거래일시 내림차순 기본.
- 무한 스크롤(서버 커서 페이징). 모바일에서 표(table) 대신 **카드형 리스트** 사용.
- 카드번호는 PG가 준 마스킹 값만 표시. 원번호 저장/표시 금지.
- 상세: 탭 시 해당 결제(paymentKey)의 승인·취소 거래 전체 이력 표시.

**불일치 내역**
- 유형 배지로 구분(아래 3장). 처리 상태: 미처리 / 확인중 / 처리완료 / 무시.
- 처리 시 담당자, 처리일시, 메모 기록(감사 로그).
- 처리 액션 예: "PG 기준으로 우리 DB 보정 요청", "망취소 확인", "정상(시차) 처리".
  실제 데이터 보정은 서버에서 권한 체크 후 수행, 앱은 요청만.

**정산 내역**
- 기준일 토글: 매출일(soldDate) / 지급일(paidOutDate).
- 지급일 기준 합계(지급 예정 금액)를 상단 고정.
- 수수료는 합계 + 상세(fees 배열 type별) 펼침.

## 3. 대사 상태·불일치 유형 (공통 코드)

| 코드 | 의미 | 흔한 원인 |
|------|------|-----------|
| MATCHED | 일치 | - |
| AMOUNT_MISMATCH | 양쪽에 있으나 금액 다름 | 부분취소 반영 누락, 할인 금액 처리 차이 |
| STATUS_MISMATCH | 금액 같고 상태 다름 | 우리 DB는 승인, PG는 취소 |
| MISSING_IN_OURS | PG에만 있음 | 승인 후 우리 DB 저장 실패(타임아웃, 서버 오류) |
| MISSING_IN_PG | 우리에만 있음 | 승인 API 실패인데 우리가 성공 처리, 테스트 데이터 |
| TIMING | 날짜 경계 차이 | 23:59 승인 → 날짜 기준 차이 (다음날 자동 해소 대상) |

TIMING은 D+1 재대사에서 해소되면 MATCHED로 바꾸고, 해소 안 되면 실제 불일치로 승격한다.

## 4. 엑셀 다운로드

- **서버에서 xlsx 생성** → 앱은 파일 URL(만료 짧은 서명 URL) 받아 다운로드 후 OS 공유 시트로 열기/저장.
  앱에서 대량 데이터 받아 직접 만들지 않는다(메모리, 속도).
- 현재 화면의 필터 조건을 그대로 넘긴다. "보이는 것 = 다운받는 것".
- 대용량(예: 1만 건 이상)은 비동기 생성 + 완료 알림.
- 시트 구성 권장: `요약`, `거래목록`, `불일치`, `정산` (요청 화면에 따라 해당 시트만).
- 개인정보: 마스킹 카드번호만, 고객 연락처는 기본 제외.
- 파일명: `{상호}_{화면}_{시작일}_{종료일}.xlsx`

## 5. 권한·보안 체크리스트

- [ ] PG 시크릿 키는 서버 환경변수/시크릿 매니저에만. 앱 번들 포함 금지.
- [ ] PG API 호출 서버 IP를 토스 "API 키 접근 정책"에 등록.
- [ ] 관리자 API는 상점(mId/store_id) 단위 권한 체크. 다른 상점 데이터 조회 차단.
- [ ] 역할 분리: 조회 전용 / 처리 권한(불일치 처리, 보정 요청).
- [ ] 엑셀 다운로드 이력(누가, 언제, 어떤 조건) 로그.
- [ ] 웹훅 수신 시 secret 검증.

## 6. 모바일 UX 규칙 (프레임워크 무관)

- 금액: 천 단위 콤마 + "원". 취소/음수는 빨간색, 마이너스 부호 명시.
- 날짜: 목록은 `MM.dd HH:mm`, 필터/엑셀은 `yyyy-MM-dd`. 서버/PG는 KST(+09:00) 기준 통일.
- 상태는 색 + 텍스트 배지 둘 다(색만으로 구분 금지).
- 당겨서 새로고침 = 우리 서버 재조회일 뿐, PG 재대사 아님. 재대사 버튼은 처리 권한자에게만, 서버 비동기 작업으로.
- 빈 상태 문구 구분: "거래 없음" vs "아직 대사 전(배치 대기)" vs "조회 실패".

## 7. 개발 순서

1. 결제 승인/취소 시 우리 `payment`, `payment_tx` 저장 구조 확정 (paymentKey, transactionKey, orderId 필수 저장)
2. PG 거래/정산 수집 배치 + 원본 저장 테이블
3. 대사 배치 + `recon_result`
4. 관리자 조회 API (요약/일별/거래/불일치/정산)
5. 엑셀 생성 API
6. 모바일 화면 (홈 → 일별 → 거래 → 불일치 → 정산 순)
7. 테스트: 아래 케이스 전부 재현 확인

### 필수 테스트 케이스
- 정상 승인 1건 / 전액 취소 / 부분 취소 2회
- 승인 직후 우리 서버 저장 실패 → MISSING_IN_OURS
- 23:59:50 승인 → TIMING → 다음날 MATCHED
- 15자리 아멕스 카드 결제 거래 표시(카드번호 길이 가정 금지)
- 0건 날짜, 1만 건 이상 기간 엑셀
